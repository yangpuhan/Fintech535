The Crossed Wheel

An algorithm is a function that takes inputs and returns open orders. This one runs every weeknight on GitHub Actions: it pulls AAPL from LSEG, reads the book Sanji wrote, and writes the next session's orders to open_orders.json in Sanji. The rule is 1.4's wheel, crossed with two other things this course taught — 1.2's lesson about earnings and this week's open-interest clusters — and it was chosen from 36 such crossings by a selection rule written down before the comparison ran.

    02The parts

    Four assignments left four findings that each suggest a change to the wheel. Each became a switch on 1.4's engine, so every combination runs on the same tape, chain, deltas, profit-take and measured fill — only the switch differs.

    3 × 3 × 2 × 2 = 36 candidates; the all-off one is 1.4's wheel. Controls run beside them: put-write, buy-write, puts-then-hold (sell puts until assigned, then never write a call), buy & hold, T-bills.

    03The lab

    The danger in crossing 36 things is picking the luckiest. So the choice was made by a rule fixed in gearwheel/lab.py before it ran:

    1. Rank all 36 by Sharpe on 1.4's window only (3 Jan 2022 – 30 Sep 2025).
    2. Take the top five. Each must (a) beat 1.4's wheel on the new tape (1 Oct 2025 on, pulled after every part was written), and (b) beat it in at least 6 of 9 robustness cells — delta 0.25 / 0.30 / 0.35 × fill k 0.30 / 0.57 / 0.80, full-period Sharpe.
    3. The winner is the highest-ranked finalist that passes both. If none does, the answer is 1.4's wheel.
    Disclosure. Two parts — the both-sides blackout and the gear — had already been run on the new tape before the lab existed (they were the first hypothesis). The rule ranks on 1.4's window, so that look could not move the ranking; it did influence which parts entered the lab.

    What each part does on its own

    For each part, every pair of candidates that differ only in that part: the average change in Sharpe it causes, and in how many pairs it helps.

    Why the gear loses: under the put-entry version (B) shares only arrive after a fall, when the market is rarely a calm uptrend, so the gear almost never acts; the buying version (A) acts — and buys after rallies, the opposite of the wheel's edge.

    The controls

    04The winner

    1.4's wheel, with two changes. Decided on the last close, every night.

    Wheel
    Flat: sell cash-secured puts on the first monthly with ≥ 21 days, as many as the cash secures. Long: one call per 100 shares, same expiry rule, at or above the cost basis (1.4's basis rule). Buy a short back once it costs half its premium.
    Earnings
    No new put or call whose life spans Apple's next report date. When LSEG has no forward date yet, the script estimates one (last report + 91 days) and widens the blackout ten days early.
    OI strike
    Among strikes whose |delta| is between 0.20 and 0.40, the one with the most open interest; ties to the nearest 0.30. Open interest is published the morning after, so the night's choice uses each contract's latest report.
    Delta
    Computed, not read: implied vol and Black-Scholes delta from each contract's last closing mid (1.3/1.4's greeks.py), because Sanji rejects delta:30 until Robin keeps chain snapshots. The strike goes to Sanji as a bare number.

    Where the blackout earns its keep

    1.4's wheel, its 77 shorts split by whether their life spanned a report. The damage is on the call side: a call held through a report is a bet that Apple does not jump, and in this sample it did.

    Option P&L per short (premium less the cost to close or the intrinsic at assignment). The lab did not get to use this split: "calls only" was one of the settings, ranked on 1.4's window, and it finished below "both sides".

    No look-ahead

    1.4's test: cut every price series at a date, re-run from scratch, compare the blotter up to that date. A rule that peeks at the future writes a different past when the future is deleted.

    05From the backtest to Sanji

    The backtest fills on the close of the session after the decision; Sanji fills at the open, or inside the day's range for a limit. The rule is the same; the plumbing differs, and each difference is written into gearwheel/orders.py.

    DecisionSanji orderWhy it is written this way
    sell the putSHT put, expiry = the date, strike = a number, lmt_prc: "mid" The rule names an exact contract the night before; a dated expiry and a bare strike need no chain on Sanji's side. Mid at the open is where 1.4 measured AAPL options print.
    sell the callSHT call, same shape, strike ≥ basis Basis = the assigned put's strike less its premium, read back from mkt/fills.json by our own order ids.
    profit-takeBTC, lmt_prc = half the entry premium A numeric limit needs no quote, and Sanji fills a buy limit when the day's low trades through it. The backtest rolls on one close; here the next short is sold the night after.
    assignment— Sanji applies it at the close; the next night reads shares in the book and writes the call.
    a run that starts lateno new orders GitHub starts scheduled runs hours late on this repo. If the last close is not the session before the one being planned, Sanji has not resolved the book yet, and planning off it is the stale-book mistake his spec warns about.
    a book it cannot readno new orders Sanji has not written a positions.json yet, so its shape is unknown. The script reads the order schema's own fields and refuses anything else rather than guess a position.

    Orders for a session not yet resolved are kept when the file is rewritten, so a second run the same day never pulls an order out from under Sanji; ids carry the action, contract and session, so a re-run writes the same id and Sanji fills it once.

    07The pipeline

    • Schedule. 03:00 UTC Tue–Sat (10pm EST, the instructor's time) plans the next session; 08:00 UTC retries. The LSEG account allows one sign-in at a time, so a run that meets an open Workspace fails and the retry tries again; the site keeps the last state.
    • Secrets. LSEG_APP_KEY, LSEG_USERNAME, LSEG_PASSWORD, opened as a platform session without sign-on control, so the job never logs the desktop app out.
    • Dry run. "Run workflow" with dry_run decides and prints the orders and commits nothing.
    • Deploy. Pages builds from main:/docs; the bot's commit is the deploy. The course server pushes price_history.json to the same branch, so the job rebases before it pushes.
    • Underlying. AAPL, conid 265598, added to this repo's price_history.json so the course server tracks it (it seeds each repo with a random name; this one got Alphabet). Same stock as 1.2–1.4, so the backtest evidence is about the thing traded.
    • Data. 1.4's tape ended 30 Sep 2025; gearwheel/backfill.py carried it to the last session before this pull with the same bands, fields and batching.
    Reproduce: the lab and backtest from the cached tape, the orders against LSEG.
